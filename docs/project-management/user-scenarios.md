# 사용자 시나리오 (User Scenarios)

**프로젝트**: A-SW Hub 플랫폼
**문서번호**: US-2025-ASW-001
**작성일**: 2025.09.01
**버전**: 1.0
**상태**: Approved

---

## 문서 개요

본 문서는 A-SW Hub 플랫폼의 주요 사용 시나리오를 정의합니다. 각 시나리오는 실제 사용자 관점에서 작성되었으며, 요구사항 검증 및 E2E 테스트의 기반이 됩니다.

---

## Persona 정의

### P1. Admin (관리자) - 김철수
- **소속**: 한국생산기술연구원 (KITECH)
- **역할**: 프로젝트 총괄 관리자
- **목표**: 5개 기관의 142개 프로젝트를 효율적으로 관리하고, 품질을 보장
- **기술 수준**: 중급 (Git, CI/CD 개념 이해)
- **사용 환경**: MacBook Pro, Chrome 브라우저

### P2. Developer (개발자) - 이영희
- **소속**: (주)비아 (VIA)
- **역할**: A-SW 플랫폼 개발자
- **목표**: 빠른 빌드/배포로 개발 주기 단축, 코드 품질 유지
- **기술 수준**: 고급 (TypeScript, SvelteKit 숙련)
- **사용 환경**: Windows 11, VS Code, Chrome

### P3. Viewer (조회자) - 박민수
- **소속**: 전북대학교 (JBNU)
- **역할**: 연구원 (비개발자)
- **목표**: 프로젝트 진행상황 모니터링, 리포트 작성
- **기술 수준**: 초급 (웹 브라우저 사용만 가능)
- **사용 환경**: iPad, Safari 브라우저

## 핵심 시나리오

### US-1. 로그인 및 대시보드 조회

**Actor**: 모든 사용자 (Admin, Developer, Viewer)
**목표**: 플랫폼에 로그인하고 프로젝트 현황 파악
**빈도**: 매일 1회 이상
**요구사항**: FR-1.1.1, FR-1.1.2, FR-6.1.1 ~ FR-6.1.5

#### 사전 조건
- 사용자 계정이 등록되어 있음
- 브라우저가 https://asw-hub.com 접속 가능

#### 시나리오 흐름

1. **로그인 페이지 접속**
   - 사용자가 `https://asw-hub.com` 접속
   - 로그인 페이지 표시 (Email/Password 폼 + GitHub OAuth 버튼)

2. **Email/Password 로그인 (방법 A)**
   - 이메일 입력: `admin@kitech.re.kr`
   - 비밀번호 입력: `SecurePass123!`
   - "로그인" 버튼 클릭
   - 서버 인증 성공 → JWT 토큰 발급
   - 대시보드로 리다이렉트

3. **GitHub OAuth 로그인 (방법 B, 대안)**
   - "GitHub으로 로그인" 버튼 클릭
   - GitHub 인증 페이지로 리다이렉트
   - GitHub 자격증명 입력 및 승인
   - 콜백 URL로 복귀 → JWT 토큰 발급
   - 대시보드로 리다이렉트

4. **대시보드 확인**
   - 상단: 사용자 이름 및 역할 표시
   - 왼쪽 사이드바: 메인 메뉴 (Projects, Builds, Deployments, Approvals, Timeline, Settings)
   - 중앙 영역:
     - 프로젝트 상태 요약 카드 (활성 프로젝트 수, 전체 프로젝트 수)
     - 빌드 성공률 그래프 (최근 30일)
     - 최근 활동 피드 (최근 5개 이벤트)
     - 언어별 프로젝트 분포 차트

#### 기대 결과
- ✅ 로그인 성공 후 2초 이내에 대시보드 로딩
- ✅ 대시보드 숫자가 실제 데이터와 일치
- ✅ 그래프가 Black & White 테마로 렌더링
- ✅ 활동 피드가 최신순으로 정렬

#### 예외 흐름
- **E1. 잘못된 비밀번호**
  - 에러 메시지 표시: "이메일 또는 비밀번호가 일치하지 않습니다"
  - 로그인 폼 유지, 비밀번호 필드만 초기화
- **E2. 세션 만료**
  - 1시간 후 자동 로그아웃
  - 로그인 페이지로 리다이렉트, 메시지: "세션이 만료되었습니다. 다시 로그인하세요."

### US-2. 신규 프로젝트 생성 및 설정

**Actor**: Admin, Developer
**목표**: 새로운 A-SW 프로젝트를 플랫폼에 등록하고 Git 저장소 연동
**빈도**: 주 1-2회
**요구사항**: FR-2.1.1, FR-2.2.1 ~ FR-2.2.5

#### 사전 조건
- 로그인 상태 (Admin 또는 Developer 역할)
- Git 저장소가 생성되어 있음 (예: `https://github.com/via-corp/asw-crop-monitor`)

#### 시나리오 흐름

1. **프로젝트 목록 페이지 이동**
   - 왼쪽 사이드바에서 "PROJECTS" 클릭
   - 프로젝트 목록 페이지 로딩
   - 우측 상단 "+ NEW PROJECT" 버튼 클릭

2. **General 정보 입력**
   - **프로젝트 이름**: `Crop Monitoring System`
   - **설명**: `실시간 작물 생육 상태 모니터링 및 자동 관개 제어 시스템`
   - **카테고리**: `작물관리` (드롭다운 선택)
   - **가시성**: `Public` (모든 참여기관이 조회 가능)

3. **Repository 설정**
   - **Git Provider**: `GitHub` (드롭다운 선택)
   - **Repository URL**: `https://github.com/via-corp/asw-crop-monitor`
   - **Default Branch**: `main`
   - "연결 테스트" 버튼 클릭 → ✅ 연결 성공 메시지 표시

4. **Build 설정**
   - **빌드 명령어**: `npm run build`
   - **Node.js 버전**: `20.x` (드롭다운 선택)
   - **환경 변수** (선택):
     ```
     VITE_API_BASE_URL=https://api.asw-hub.com
     VITE_ENABLE_MOCK=false
     ```

5. **Deployment 설정** (선택)
   - **배포 환경**: `Staging`
   - **타겟 URL**: `https://staging-crop.asw-hub.com`
   - **자동 배포**: `On` (체크박스 선택)

6. **Notifications 설정** (선택)
   - **빌드 완료 알림**: ✅ Email, ✅ Slack
   - **Slack Webhook URL**: `https://hooks.slack.com/services/T00000000/B00000000/XXXXXXXXXXXXXXXXXXXX`

7. **프로젝트 생성 완료**
   - "CREATE PROJECT" 버튼 클릭
   - 서버 유효성 검증
   - 프로젝트 생성 성공 → 프로젝트 상세 페이지로 리다이렉트
   - 성공 토스트 메시지: "프로젝트가 성공적으로 생성되었습니다"

#### 기대 결과
- ✅ 프로젝트가 DB에 저장됨
- ✅ 프로젝트 ID 자동 생성 (UUID)
- ✅ Git 저장소 연결 성공 (Webhook 자동 생성)
- ✅ 프로젝트 목록에 새 프로젝트 표시
- ✅ 생성자가 자동으로 Owner 권한 부여

#### 예외 흐름
- **E1. 중복된 프로젝트 이름**
  - 에러: "동일한 이름의 프로젝트가 이미 존재합니다"
  - 이름 필드에 포커스, 빨간 테두리 표시
- **E2. 잘못된 Git URL**
  - "연결 테스트" 실패
  - 에러: "저장소에 접근할 수 없습니다. URL을 확인하세요."
- **E3. 필수 필드 누락**
  - "CREATE PROJECT" 버튼 비활성화
  - 누락된 필드에 "필수 항목입니다" 메시지 표시

### US-3. CI/CD 빌드 트리거 및 로그 모니터링

**Actor**: Developer
**목표**: 코드 푸시 후 자동 빌드 확인 또는 수동 빌드 실행, 실시간 로그 확인
**빈도**: 하루 5-10회 (개발 중)
**요구사항**: FR-3.1.1 ~ FR-3.1.7, FR-3.2.1 ~ FR-3.2.5

#### 사전 조건
- 프로젝트가 생성되어 있음
- Git 저장소에 코드가 존재
- Developer 권한 보유

#### 시나리오 흐름 (자동 빌드)

1. **코드 푸시**
   - 개발자가 로컬에서 코드 수정
   - Git 커밋: `git commit -m "feat: Add crop health prediction API"`
   - Git 푸시: `git push origin main`

2. **Webhook 트리거**
   - GitHub Webhook이 A-SW Hub에 이벤트 전송
   - 플랫폼이 자동으로 빌드 큐에 추가
   - 빌드 상태: `Pending` → `Running`

3. **빌드 실행 알림**
   - 브라우저 내 알림: "Crop Monitoring System 빌드 시작 (커밋: a1b2c3d)"
   - 이메일 알림: "빌드 #42가 시작되었습니다"

4. **빌드 로그 페이지 이동**
   - 알림 클릭 → 빌드 로그 페이지로 이동
   - URL: `/builds/42`

5. **실시간 로그 스트리밍 확인**
   - 9개 섹션으로 구분된 로그:
     1. ✅ Clone Repository (5초)
     2. ✅ Install Dependencies (23초)
     3. ✅ Lint & Type Check (8초)
     4. 🔄 Build (진행 중... 현재 15초 경과)
     5. ⏸️ Test (대기 중)
     6. ⏸️ Package
     7. ⏸️ Upload Artifacts
     8. ⏸️ Deploy to Staging
     9. ⏸️ Verify Deployment

   - 각 섹션 클릭 시 접기/펼치기 가능
   - "EXPAND ALL" / "COLLAPSE ALL" 버튼으로 전체 토글

6. **빌드 완료**
   - 모든 단계 완료 (총 소요 시간: 1분 42초)
   - 빌드 상태: `Running` → `Success`
   - 성공 토스트 메시지: "빌드 #42가 성공적으로 완료되었습니다"
   - 이메일 알림: "빌드 #42 성공 (1분 42초)"

#### 시나리오 흐름 (수동 빌드)

1. **프로젝트 상세 페이지 이동**
   - Projects 목록에서 "Crop Monitoring System" 클릭

2. **빌드 트리거**
   - 우측 상단 "TRIGGER BUILD" 버튼 클릭
   - 확인 모달: "main 브랜치를 빌드하시겠습니까?"
   - "CONFIRM" 버튼 클릭

3. **빌드 실행**
   - 빌드 큐에 추가
   - 자동으로 빌드 로그 페이지로 리다이렉트
   - (이후 흐름은 자동 빌드와 동일)

#### 기대 결과
- ✅ 빌드 로그가 1초 이내 업데이트
- ✅ 각 단계별 소요 시간 표시
- ✅ 터미널 스타일 (검정 배경 + 녹색 텍스트)
- ✅ 로그 다운로드 가능 (.txt 파일)
- ✅ 빌드 성공 시 Staging 자동 배포

#### 예외 흐름
- **E1. 빌드 실패 (Lint 에러)**
  - 3단계 "Lint & Type Check"에서 실패
  - 에러 로그:
    ```
    ✘ [ERROR] TypeScript error in src/lib/api/crop.ts:42:15
      Type 'number' is not assignable to type 'string'
    ```
  - 빌드 상태: `Failed`
  - 실패 알림: "빌드 #42 실패 - TypeScript 에러 1건"
  - "RETRY BUILD" 버튼 표시

- **E2. 빌드 타임아웃 (10분 초과)**
  - 빌드 자동 취소
  - 에러: "빌드가 시간 초과로 중단되었습니다 (10분)"
  - 빌드 상태: `Timeout`

### US-4. 배포 승인 워크플로우

**Actor**: Developer (요청자), Admin (승인자)
**목표**: Production 배포 전 2단계 승인 절차 수행
**빈도**: 주 1회 (스프린트 종료 시)
**요구사항**: FR-4.1.3, FR-5.2.1 ~ FR-5.2.5

#### 사전 조건
- Staging 배포가 성공적으로 완료됨
- Staging 환경에서 테스트 완료

#### 시나리오 흐름

**Phase 1: Developer 승인 요청**

1. **배포 요청 생성**
   - Deployments 페이지 이동
   - "NEW DEPLOYMENT REQUEST" 버튼 클릭
   - 폼 입력:
     - **프로젝트**: `Crop Monitoring System`
     - **환경**: `Production`
     - **버전**: `v1.2.0` (Git 태그)
     - **제목**: `Sprint 12 Release - Crop Health Prediction`
     - **설명**:
       ```
       주요 변경사항:
       - 작물 건강도 예측 API 추가 (ML 모델 v2.1)
       - 대시보드 성능 개선 (로딩 시간 30% 단축)
       - 버그 수정 3건 (#123, #124, #125)

       테스트 결과:
       - Unit Test: 127/127 통과 (100%)
       - E2E Test: 18/18 통과 (100%)
       - Staging 환경 3일간 안정성 검증 완료
       ```
     - **첨부 파일**: `test-report.pdf` (업로드)

2. **승인 요청 제출**
   - "SUBMIT REQUEST" 버튼 클릭
   - 요청 ID 생성: `APR-2025-042`
   - 1차 승인자(Developer Role) 자동 할당: 이영희 (본인)
   - 2차 승인자(Admin Role) 자동 할당: 김철수

3. **1차 승인 (Developer 본인)**
   - Approvals 페이지로 이동
   - "Pending My Approval" 탭에서 `APR-2025-042` 확인
   - "REVIEW" 버튼 클릭
   - 검토 후 "APPROVE" 버튼 클릭
   - 댓글 입력: "Staging 환경 검증 완료. Production 배포 준비 완료."
   - 승인 완료 → 상태: `Pending` → `Developer Approved`

**Phase 2: Admin 최종 승인**

4. **Admin 알림 수신**
   - 김철수(Admin)가 이메일 수신: "새로운 승인 요청이 도착했습니다 (APR-2025-042)"
   - 플랫폼 로그인 → 알림 센터에 빨간 배지 표시 (1)

5. **승인 요청 검토**
   - Approvals 페이지 → "Pending My Approval" 탭
   - `APR-2025-042` 클릭하여 상세 조회
   - 변경사항, 테스트 결과, 첨부 파일 검토
   - Staging 환경 직접 확인 (브라우저에서 테스트)

6. **최종 승인**
   - "APPROVE" 버튼 클릭
   - 댓글 입력: "변경사항 검토 완료. Production 배포 승인합니다."
   - 승인 완료 → 상태: `Developer Approved` → `Approved`

7. **자동 배포 실행**
   - 승인 완료 즉시 자동으로 Production 빌드 트리거
   - 빌드 #43 시작
   - 빌드 성공 → Production 배포 자동 실행
   - 배포 완료 → 상태: `Deployed`
   - Slack 알림: "✅ Crop Monitoring System v1.2.0이 Production에 배포되었습니다"

#### 기대 결과
- ✅ 2단계 승인 절차 정상 동작
- ✅ 각 단계별 이메일 알림 발송
- ✅ 승인 히스토리 추적 (누가, 언제, 무엇을)
- ✅ 승인 완료 후 자동 배포 실행

#### 예외 흐름
- **E1. Admin 거부**
  - "REJECT" 버튼 클릭
  - 거부 사유 입력 (필수): "테스트 커버리지가 목표(90%) 미달입니다 (현재 85%). 추가 테스트 후 재요청 바랍니다."
  - 상태: `Rejected`
  - 요청자(Developer)에게 이메일 알림: "승인 요청이 거부되었습니다"
  - Developer는 수정 후 재요청 가능

- **E2. 배포 중 실패**
  - 배포 단계에서 Health Check 실패
  - 자동 롤백: 이전 버전(v1.1.0)으로 복구
  - 상태: `Deploy Failed`
  - 긴급 알림: 이메일, Slack, SMS (Admin에게)
